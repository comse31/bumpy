## Что делает решатель

`tools/solve_level.py` строит дискретную модель движения шара и правил игровых элементов (по
`main/levels.json`, зеркаля `main/ball/ball.script`, `main/platforms/*`, `main/walls/*`) и ищет
**оптимальную последовательность действий игрока**, проходящую уровень.

### Целевая функция (лексикографическая, 3 уровня)

1. **Минимум предметов на старте** — `min sum(required)` (drops / keys / hammers, которые надо иметь
   до уровня). Главный критерий.
2. **Максимум подобранных расходников** — `max collected` (капельки/ключики/молоточки, коды 1/2/3;
   сердечки кода 4 не считаются).
3. **Минимум действий** — `min actions`.

### Ключевые свойства модели

- Сетка 6×6, экранные координаты (row 0 — низ). Состояние: позиция шара + вид опоры
  (`plat` / `blocktop`). Действия: боковой хоп, высокий прыжок с отводом на одну колонку в сторону,
  разбивание стены/блока, касание выхода.
- Ресурсы: ключи — на серые перегородки (один ключ на удар, прочность 1–3), hammer — на кирпичную
  кладку, drop — на горящие. Ресурсы можно «занимать»; стартовый запас = `required`.
- **Кирпичная кладка (block, 8 рядов, код 10)**: удержание прыжка автоматически повторяет высокие
  прыжки, поэтому с обычной/липкой платформы одно действие доводит кладку до разрушения (1 молоток).
  С **схлопывающейся** панели авто-повтора нет: действие сбивает один ряд и тратит использование
  панели, панель может исчезнуть, шар падает на поверхность ниже и продолжает бить кладку оттуда
  (каскад). Первый удар по кладке расходует один молоток.
- **Shrinkable-платформа**: расходуется действием с неё; прочность lo 2/3/4 = 3/2/1 использований
  (коды 3 и 4 — предварительно повреждённые). Исчерпанная панель не блокирует: приземлиться нельзя,
  но ячейка проходима (шар пролетает вверх/вниз).
- **Sticky-платформа**: если в момент касания удерживать прыжок, шар прыгает высоко бесконечно
  (авто-повтор, как на обычной); если не удерживать — залипает и может только соскочить вбок.
  Игрок всегда может удерживать, поэтому для планирования липкая ведёт себя **как обычная платформа**
  (в т.ч. кладка над ней — за одно действие).
- **Slope** перенаправляет приземление на одну клетку в сторону наклона (наклон в край поля — обычный
  отскок); старт на наклонной сразу сносит шар на клетку в сторону (без действия игрока).
- Выход открывается после сбора `timer` коллектиблов (фрукты, код ≥5); платформа в клетке выхода
  удаляется; касание выхода засчитывается на любом контакте, в т.ч. на смертельном ходу.

### Сверка с правилами игры и принятые упрощения

Модель сверена с кодом игры репозитория (эталон для решателя) и с логом реального прохождения
(`tools/52 level.log`). Совпадает: цель (сбор `timer` коллектиблов → выход; расходники не нужны),
обычный/высокий прыжок, наклонные, исчезающие прочности, горящие/капля, серые перегородки/ключи,
кладка/молоток (первый удар −1 молоток, ряды), авто-повтор высокого прыжка при удержании, липкие
(удержание → бесконечные прыжки, иначе залипание), верх кладки без высокого прыжка.

Осознанные упрощения (не мешают валидному прохождению одного уровня, но полезно знать):
- **Жизни и respawn не моделируются**: шипы/падение = `DEAD` (невалидный путь), а не потеря жизни с
  перезапуском и откатом кармана. «Пожертвовать жизнью» решатель не умеет.
- **Сердечки (код 4) игнорируются** (в игре добавляют жизнь).
- **Перенос кармана между уровнями не моделируется**: `required` считается по уровню.

### Алгоритм поиска

Lexicographic Dijkstra (label-setting) по `(состояние, мир)` с Pareto-фронтом недоминируемых меток
`(required, actions)`; цель лексикографическая. Приоритет очереди — `(sum(required), actions + h,
actions)`, где `h` — максимум из «колоночного интервала» и оптимистичного all-pairs расстояния,
игнорирующего опасности. Мир упакован в маленькие целые (durability стен и shrink — 2-битные, урон по
блокам — 4-битные, маски «блок получал удар» / сожжённых / собранных), пройденные клетки — 36-битная
маска. При исчерпании `node_cap` — жадный fallback, затем «последняя надежда» (поиск со старой целью:
минимум стартовых предметов → действий); результат помечается `optimal=False`.

**Почему критерий №2 дорог:** `collected` входит в мир (битмаска), поэтому до доказательства максимума
собранного нельзя останавливаться на первой цели — поиск исследует все состояния со стартовым набором
не больше лучшего.

## Методика бенчмарка

```
python3 tools/bench_solve.py --node-cap 300000        # все 100 уровней
```

`tools/bench_solve.py` прогоняет уровни 1..100, пишет `tools/levels_data.json` и сортируемый
HTML-отчёт `tools/levels_report.html` (в т.ч. колонка **«Собрано %»** = собрано / всего расходников).
«Оценка сложности» 0..100 — взвешенная сумма структурных факторов:

```
25 * min(required_items,8)/8            # давление ресурсов
25 * min(spikes+burning,36)/36          # плотность опасностей
15 * min(destructible_walls+blocks,18)/18  # плотность препятствий
10 * min(slopes+shrink,36)/36           # нестабильность поверхностей
10 * log10(nodes)/log10(node_cap)       # сложность маршрута (усилие поиска)
10 * min(actions,60)/60                 # длина исполнения
 5 * min(collectibles,16)/16            # нагрузка сбора
```

Классы: `<=15 easy`, `<=30 medium`, `<=50 hard`, иначе `expert`. Оценка сложности — эвристика для
сортировки, а не метрика времени поиска.

## Что именно нужно оптимизировать (гипотезы для проверки)

1. **Критерий №2 («максимум собранного») — главный источник взрыва.** `collected` входит в мир,
   поэтому поиск исследует все состояния с `required <= R*`. Направления:
   - **доминирование по включению множеств**: если мир отличается только набором собранного и один
     набор — надмножество другого, надмножество не хуже; хранить только максимальные по включению.
   - **верхняя граница собранного**: «собрано сейчас + всё оставшееся» как оценка сверху; если она не
     превышает лучшую цель — узел отсекается.
   - **двухфазность**: сначала точно минимизировать `required` (быстро, как раньше), затем отдельным
     проходом максимизировать `collected` в пределах `sum(required) = R*`, затем действия.
2. **Взрыв состояния из-за shrink-платформ.** Канонизация миров (неиспользуемые остатки, недостижимые
   клетки), более точная эвристика — сокращают число ключей.
3. **Каскадное разбивание кладки.** Частичный урон (4 бита на блок) добавляет состояния; уровни
   L26/L34/L39 дороже всех. Направление: компактнее хранить урон, отдельная обработка «башен» кладок.
4. **Слабая эвристика `h`.** Не учитывает ключи/молотки/drops, кладки, стоимость сбора. Добавить:
   обязательные затраты ресурсов, land-based оценку, оценку обязательных ударов по кладкам,
   pattern-database/предоценки.
5. **Доминирование меток.** Линейный скан по списку меток ключа; рассмотреть структуру для 3D-Pareto
   (`required`) + время, ε-доминирование.
6. **Fallback и «последняя надежда».** Жадный fallback проваливается на L26 (спасает поиск со старой
   целью, 611k узлов, 31 с). Улучшить fallback (beam search, локальные улучшения, IDA*).
7. **Адаптивный `node_cap` / IDA*** для 14 fallback-уровней.
8. **Микрооптимизация Python**: `successors`, `add_label`, `heuristic`, `floor_at`, `landing`,
   `block_broken`/`block_hit` — аллокации `namedtuple._replace`, повторные `bit_count()`.

## Жёсткие ограничения (нельзя нарушать)

- Решатель возвращает **лексикографически минимальный** план: (1) `min sum(required)`,
  (2) `max collected` (расходники кодов 1–3), (3) `min actions`. Менять оптимум допустимо только как
  явно помеченный «неоптимальный fallback».
- Правила игры и модель должны остаться корректными: движение; стены/ключи; кладка/молоток (1 действие
  при авто-повторе удержания с обычной/липкой платформы; по ряду со shrink; каскад при исчезновении
  панели); горящие/drop; slope (и снос на спавне); shrink с проходимой исчерпанной ячейкой; липкие
  (удержание → авто-повтор, иначе залипание, но планируется как обычная); верх кладки без высокого
  прыжка.
- Интерфейс `solve(level, node_cap, stats, ...)` и поля результата (`status`, `reason`, `actions`,
  `required`, `used`, `collected`, `items`, `nodes`, `optimal`, `stats`) используются
  `tools/bench_solve.py` и `tools/test_solver.py` — сохрани их (или обнови и бенчмарк, и тесты).
- Есть регрессионные тесты `tools/test_solver.py` (сверка с полным перебором; «больше собранного при
  равном стартовом наборе»; кладка за 1 действие; по ряду со shrink; старт на липкой). Оптимизация не
  должна их ломать.
