## Роль и задача

Ты — эксперт по алгоритмам поиска (пространство состояний, label-setting / Dijkstra, Pareto-фронты,
допустимые эвристики, канонизация состояний) и по оптимизации Python.

Отчёт по бенчмарку решателя пазл-игр `tools/solve_level.py` на 100 уровнях. Нужно **предложить и
обосновать оптимизации**, чтобы решатель:

1. решал **все 100 уровней** кратно быстрее (сейчас CPU 312.2 с, на 16 ядрах wall 28.1 с);
2. **доказывал оптимальность** на большем числе уровней (сейчас 87/100; 13 — fallback);
3. не терял корректности (валидный план, точные `required`/`used`/`collected`).

Дополнительно (будущее): решатель будет **оракулом решаемости в генераторе уровней** (размер карты,
сложность, seed → уровень → решатель проверяет, решаемый ли он). Там критична скорость
`solvable/impossible` и параллелизм по кандидатам, а не доказательство оптимальности.

Верни: (а) диагноз, (б) 3–7 ранжированных идей с оценкой эффекта/риска, (в) псевдокод/патч ключевых
функций, (г) план проверки. Не начинай с C++/Numba/GPU: сначала сокращение объёма поиска.

## Что делает решатель

Строит дискретную модель движения шара и правил игровых элементов (по `main/levels.json`, зеркаля
`main/ball/ball.script`, `main/platforms/*`, `main/walls/*`) и ищет **оптимальную последовательность
действий игрока**.

### Целевая функция (лексикографическая, 3 уровня)

1. `min sum(required)` — минимум drops/keys/hammers на старте;
2. `max collected` — максимум подобранных расходников (коды 1/2/3; сердечки кода 4 не в счёт);
3. `min actions` — минимум действий.

### Ключевые правила модели

- Сетка 6×6, экранные координаты (row 0 — низ). Состояние: позиция шара + вид опоры
  (`plat` / `blocktop`).
- **Кладка/перегородка схлопываются в одно действие ТОЛЬКО со стабильной поверхности**: начал ломать —
  доломает (кладка снизу: 1 действие + 1 молоток; перегородка сбоку: 1 действие + остаточная прочность
  в ключах). **Со shrink-панели схлопывать нельзя**: панель тратит использование, может исчезнуть, шар
  падает ниже и продолжает (кладка — по ряду, перегородка — по удару), может и проиграть.
- Shrinkable: расходуется действием с неё, прочность lo 2/3/4 = 3/2/1; исчерпанная ячейка проходима.
- Sticky: удержание прыжка при касании → авто-повтор высоких прыжков (для планирования = обычная
  платформа); без удержания — залипание. Игрок всегда может удерживать.
- Slope перенаправляет приземление на клетку в сторону наклона; старт на наклонной сносит шар сразу.
- Выход открывается после сбора `timer` коллектиблов (фрукты, код ≥5); касание на любом контакте, в т.ч.
  на смертельном ходу.
- Шипы/падение = `DEAD`. Жизни/respawn, сердечки, перенос кармана между уровнями **не моделируются**.

### Алгоритм

Lexicographic Dijkstra (label-setting) по `(состояние, мир)`; Pareto-фронт недоминируемых
`(required, actions)` на ключ. Приоритет `(sum(required), actions + h, actions)`. Мир упакован:
прочность стен и shrink — 2-битные, урон по блокам — 4-битные, маски «блок получал удар» / сожжённых /
собранных; пройденные клетки — 36-битная маска. При исчерпании `node_cap` — жадный fallback, затем
«последняя надежда» (поиск со старой целью); результат помечается `optimal=False`.

**Почему критерий №2 дорог:** `collected` входит в мир (битмаска), поэтому до доказательства максимума
сборки нельзя останавливаться на первой цели — поиск исследует все состояния с `required ≤ R*`.

**Быстрый оракул**: `is_solvable(level, node_cap)` — первая достигнутая цель (+ fallback), возвращает
`"solvable" | "impossible" | "limit"`. Для генератора.

## Методика бенчмарка (с параллелизмом)

```
python3 tools/bench_solve.py --node-cap 300000 --jobs 16
```

Уровни **полностью независимы** → пул процессов (`--jobs auto` = min(cpu,16)), тяжёлые первыми по
числу узлов прошлого прогона. `bench_solve.py` пишет `tools/levels_data.json` и HTML-отчёт.

«Оценка сложности» 0..100 = `25·ресурсы + 25·опасности + 15·препятствия + 10·нестабильность +
10·log10(узлов) + 10·длина + 5·сбор` (нормированные). Классы: `≤15 easy, ≤30 medium, ≤50 hard, иначе
expert`.

## Что оптимизировать дальше (с учётом findings этой сессии)

1. **Канонизация мира (пространства ПРЕПЯТСТВИЙ) — главный резерв.** Рост даёт именно набор состояний препятствий (остатки shrink/стен и урон кладки), а не подмножества `collected`. На L26 `unique_keys == labels` и `peak_front = 1`:
   доминирование меток не работает, идёт перебор сырых `(состояние, мир)`. Объединять состояния,
   эквивалентные относительно будущего (достижимость, ресурсы, будущий сбор). Только доказанная
   эквивалентность, нельзя просто выкинуть `shrink`/`collected` из ключа.
2. **Сильная эвристика.** Текущая `h` построена по графу без стен/блоков и **недопустима** (эмпирически:
   граница на `actions + h` давала регрессии L37/L61). Либо починить, либо не использовать в решениях о
   корректности. Учесть обязательные кладки/стены/каскады.
3. **Отсечка по второму критерию.** «collected now + всё несобранное» **вакуумна** (равна общему числу
   расходников). Работает только когда лучший план уже собрал максимум — отсекать по
   `actions > best_actions` (sound). Иначе нужна достижимость оставшихся предметов (связано с п.1).
4. **Макро-переход «пробить кладку/перегородку»** с корректным воспроизведением каскада над shrink
   (ряды, падения, касание выхода на смертельном ходе) — иначе остаются длинные цепочки состояний.
5. **Pareto-фронт меток** (быстрый путь для длины 0/1, компактный формат, статистика) — если `peak_front`
   где-то велик (в основном он 1, эффект мал).
6. **Разделить доказательство критериев** (A: min required; B: max collected при `R=R*`; C: min actions)
   с переиспользованием результатов.
7. **Fallback / «последняя надежда»** улучшить (beam / локальные улучшения / IDA*).
8. **Компактные узлы** (код+параметры действия вместо текста).
9. **Для генератора**: `is_solvable` уже есть; параллелить по кандидатам, tri-state (`limit` → ретрай).

**Не начинать** с C++/Numba/GPU: узкое место — объём состояний, а не арифметика.

## Жёсткие ограничения

- План **лексикографически минимален**: (1) `min sum(required)`, (2) `max collected` (коды 1–3),
  (3) `min actions`. Менять оптимум — только в явно помеченном fallback.
- Правила: кладка/перегородка — одно действие ТОЛЬКО со стабильной поверхности, со shrink — пошагово
  с падением; shrink-проходимость; липкие (удержание→авто-повтор, иначе залипание); наклонные (снос на
  спавне); горящие/drop; шипы; верх кладки без высокого прыжка.
- Интерфейс `solve(level, node_cap, stats, ...)`, поля результата (`status`, `reason`, `actions`,
  `required`, `used`, `collected`, `items`, `nodes`, `optimal`, `stats`) и `is_solvable(level,
  node_cap)` используются `bench_solve.py`/`test_solver.py`; сохрани или обнови вместе с тестами.
- Тесты `tools/test_solver.py` (полный перебор на малых уровнях; больше сбора при равном старте;
  кладка/перегородка — 1 действие со стабильной поверхности и пошагово со shrink; старт на липкой).
  Оптимизация не должна их ломать. Проверка полного прогона: эталонный JSON, сравнение кортежа
  `(sum(required), -collected, actions)` там, где оба прогона доказали оптимальность.

### Неуспешные/отброшенные попытки — чтобы не повторять

1. **Простая граница по собранному** `current + remaining < best_collected` — **вакуумна**:
   `current + remaining` всегда равно общему числу расходников уровня, поэтому условие никогда не
   срабатывает. Нужна оценка реально достижимых оставшихся предметов (это уже про канонизацию мира).
2. **Отсечка по `actions + h > best_actions`** — **незвуковая**: `h` недопустима, и отсечка меняла
   ответ (L37: 17→18, L61: 14→15, L100: 19→25). Оставлена только звуковая версия `actions > best_actions`.
3. **Доминирование по включению `collected`** — концептуально верное (физика зависит от мира только
   через препятствия + флаг «выход открыт»), но на этом корпусе не даёт выигрыша: взрыв идёт от
   пространства **препятствий** (36 shrink-клеток и т.п.), а `unique_keys ≈ labels` и `peak_front`
   мал; при этом линейный скан фронта на части уровней раздувается. Откатили.
4. **«Ленивые» подписи** и **2D-индексы** — не дали заметного ускорения; первое отброшено, второе
   оставлено как нейтральное.

### Важные находки

- **`h` недопустима** (замерено: `h(start) > оптимум` на 12 уровнях; напр. L79: 12 при оптимуме 1,
  L48: 30 при 13). Причины: цепочки наклонных панелей двигают шар на колонку **без действия игрока**,
  а коллектиблы можно собрать **пролётом**, не приземляясь. Поэтому `h` используется только для
  порядка очереди, но не для решений о корректности.
- **Доминирование меток почти не работает**: на тяжёлых уровнях `unique_keys == labels`, `peak_front`
  = 1..12. То есть перебираются сырые `(состояние, мир)`, а не конкурирующие метки.
- **Главный источник роста — пространство препятствий**: остатки shrink, прочность стен, урон кладки.
  Критерий №2 лишь заставляет исследовать все состояния с `required ≤ R*`; подмножества `collected`
  при этом почти не создают новых ключей.
- **Кэп добивается на 13 уровнях** (6,14,16,17,19,26,30,34,39,51,69,87,88); на L26 последняя надежда
  находит план на ~611k узлов. Именно эти уровни определяют wall-time.
