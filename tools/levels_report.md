# Описание уровней Bumpy (1989, Loriciels) — результаты анализа образов

Дата: 2026-10-12. Источники: `Bumpy (1989)(Loriciels).z80` (снапшот), [`tools/Bumpy.tap/BUMPY.TAP`](Bumpy.tap/BUMPY.TAP) (загрузочный образ, авторитетный), [`Bumpy-levels.png`](../Bumpy-levels.png) (контактная таблица всех 100 экранов уровней). Единственный рабочий инструмент: [`tools/level_tool.js`](level_tool.js) — декодер PNG + классификация платформ/спрайтов по пикселям.

> Примечание: промежуточные дампы-доказательства (`.txt`/`.json`) удалены при уборке `tools/`; все ключевые цифры и выводы приведены непосредственно в тексте отчёта ниже.

## 1. Что точно установлено (подтверждено байтами исходников)

### 1.1. Структура загрузки уровня — LDIR, 42 байта на уровень

В коде игры найдены две подряд идущие подпрограммы-«загрузчики» таблицы уровня:

**Загрузчик №1** — LDIR @ `0x3593` (raw-байты):
```
dd 21 2a c5   ; LD IX,0xC52A     <- базовый адрес таблицы уровней A
dd 19         ; ADD IX,DE        ; + индекс уровня (DE)
dd 66         ; LD H,(IX+0)      ; чтение первого байта ячейки
...
11 35 ab      ; LD DE,0xAB35     <- рабочий RAM: назначение
01 18 00      ; LD BC,0x0018     ; 24 байта
ed b0         ; LDIR             ; блок 0xC52A+idx -> 0xAB35 (24 B)
```

**Загрузчик №2** — LDIR @ `0x40a3` (raw):
```
dd 21 cc c5   ; LD IX,0xC5CC     <- базовый адрес таблицы уровней B
dd 19         ; ADD IX,DE
...
11 4d ab      ; LD DE,0xAB4D     ; = 0xAB35 + 24 (сразу после первого блока)
01 12 00      ; LD BC,0x0012     ; 18 байт
ed b0         ; LDIR             ; блок 0xC5CC+idx -> 0xAB4D (18 B)
```

**Что доказано:** назначения двух блоков в рабочем RAM **непрерывны** — `0xAB35..0xAB4C` (24 B) сразу за ними `0xAB4D..0xAB5A` (18 B). Значит, во время игры уровень занимает **42 байта подряд** в RAM (`0xAB35..0xAB5A`). Это твёрдый факт.

**Что НЕ доказано (открыто):** как устроены *источники*. Базы `0xC52A` и `0xC5CC` различаются на `0xA2` (162), что не совпадает ни с 24, ни с 42. Возможные варианты:
- **одна** таблица из 100 записей по 42 B, где DE второго вызова = DE первого + смещение (т.е. `0xC5CC` — это «та же» таблица, но второй сегмент берётся со своим сдвигом индекса);
- **две** отдельные таблицы: A (шаг 24, база `0xC52A`) и B (шаг 18, база `0xC5CC`).

DE (индекс уровня) в обоих случаях формируется вызывающим кодом. **Точная раскладка источников = первый пункт «что дальше» (§5).** До этого момента формулировка «42 B/уровень» верна для RAM-представления, но не гарантирует 42 B в *хранении*.

Смежные переменные состояния: `0xAA13` — флаг/счётчик уровня (проверка `fe 00` рядом с LDIR), `0xAB1C` — проверочная переменная во втором загрузчике. Обе области RAM (`0xAA00`, `0xAB00`) **не входят** в снапшот `.z80` (см. §2).

### 1.2. Снапшот `.z80` усечён — таблиц уровней в нём НЕТ
- реальный размер файла = **36677 байт** = 32 (заголовок) + 36645 байт памяти;
- память покрывает Z80-адреса **`0x0000..0x8f24`** только;
- `0xC52A`, `0xAB35`, `0xAA13`, `0xBA2B` — все **OUT OF RANGE**.

То есть любой «поиск уровней» прямо в `.z80` обречён: таблицы лежат в верхней части RAM Spectrum, которая не была захвачена. Работать нужно с TAP.

## 2. Загрузочный образ `BUMPY.TAP`
- Размер **45878 байт** (0xB336). Это НЕ стандартный TAP: заголовок — кастомный контейнер (`13 00 00 00` + `"BUMPY     "`), далее TOC, затем данные.
- TOC содержит адреса загрузки: `0x5C48, 0x5C8D, 0x5C37, 0x0080, 0x61A7, 0x61A8, 0x5C85, 0xAB7C`. **Ни один из них не равен `0xC52A`/`0xC5CC`** — игра использует memory mapper / нестандартные блоки для верхней RAM.
- Стандартный обход TAP-блоков ломается на первом же блоке (`type=0x9d len=4360`, затем OVERFLOW).

### 2.1. Критическое: маппинг «файл → память» кусочный (piecewise)
Совмещение характерных окон кода (присутствующих и в `.z80`, и в TAP) показывает, что константа сдвига `file = mem + off` **меняется от 0x42d9 до 0x47b2** по мере продвижения по памяти `0x4bd8..0x6b58` (доминирующий кластер — 0x454a, 150 окон). Следствия:
1. Сравнивать TAP и `.z80` побайтово «по одному сдвигу» нельзя.
2. Таблицы уровней при `0xC5xx` (выше всех заанкоренных адресов) **не локализуются** по кодовым якорям — этот путь закрыт.

## 3. Где же сами описания уровней? Честный статус

Игра содержит **100 уровней** (подтверждено пользователем). Если бы они хранились как непрерывная таблица «по байту на ячейку» (6×6 = 36 B/уровень), в образе должен был бы быть непрерывный проход малых байтов длиной ≈ **3600**; при схеме LDIR (42 B/уровень) — ≈ **4200**.

Максимальные проходы байтов `<= 0x1f` в TAP:
```
@0x63dd len=512   @0xac8a len=282   @0x2169 len=237   @0x5059 len=212
```
**Ни 3600, ни 4200 нет.** Выводы (важно не переоценивать):

1. Таблицы уровней **не хранятся в TAP как простой непрерывный массив 36- или 42-байтовых записей**. Возможные объяснения:
   - данные упакованы/сжаты (RLE, delta, pack-bit) и распаковываются кодом при загрузке;
   - уровни генерируются из компактного описания (сиды + правила) — типично для 48K-игр 1989 г.;
   - таблица лежит внутри большого кодового блока `type=0x9d len=4360` и «маскируется» байтами кода.
2. Ранее выдвинутая гипотеза «кодирование byte-per-cell, 36 B/уровень — подтверждено» **не подтверждена** как факт хранения: она объясняет лишь отдельные аккуратные паттерны в смешанной области данных (см. §4), но непрерывной таблицы нет. Гипотезу стоит считать **рабочей для интерпретации ячеек**, а не описанием размещения.

## 4. Кандидатные сетки 6×6 (эвристика, НЕ финальные данные)

Скольжение 36-байтовым окном по области `0x4600..0x6600` с оценкой «похожести на сетку» (все байты ≤ 0x1f, заполнено 4..32 ячеек) и отбором локальных максимумов дало: **2124 окна с score>0 → 36 кандидатов**.

Пример самого «чистого» кандидата (file `0x5455`):
```
.  .  .  .  .  .
.  .  .  .  .  .
.  .  0c  0c  0c  0c
.  02  03  03  03  03
.  0c  0c  0c  0c  0c
.  .  04  04  04  04
```
Ступенчатая структура платформ правдоподобна; при альтернативном nibble-распаковке тот же байтовый поток даёт шахматку — в пользу byte-per-cell как *формата ячеек*.

**Гистограмма значений ячеек по всем 36 кандидатам:** частые коды `0x02`(78), `0x04`(73), `0x12`(69), `0x01`(37), `0x03`(35), `0x10`(33), `0x07`(31), `0x05`(27), `0x16`(24)… вплоть до `0x31`. Маппинг «код → тип объекта» (платформа/стена/предмет) **не установлен** — для этого нужен либо рендер уровня в эмуляторе, либо дизассембли кода отрисовки ячеек.

> Кандидаты использовать как подсказки, не как финальные данные уровней.

## 5. Что делать дальше (по приоритету)
1. **Эмуляция TAP в FUSE/zx70 и дамп RAM `0xC52A..0xC8xx` во время игры** — единственный надёжный способ получить все 100 описаний уровней «как их видит игра». Загрузить `BUMPY.TAP`, дождаться старта уровня, снять память. (Вне возможностей текущего окружения — нужен эмулятор.)
2. **Дизассембли вызывающего кода LDIR-загрузчиков** (`0x3578..0x3593` и `0x4060..0x40a3` в `.z80`, оба диапазона на месте): определить, как формируется DE (шаг между уровнями) и откуда берётся номер уровня. Это снимет вопрос «24+18: одна таблица или две».
3. **Найти код отрисовки/интерпретации ячеек** (цикл по 36 ячейкам рабочего RAM `0xAB35..`) и зафиксировать таблицу соответствия «значение ячейки → спрайт/поведение» — это даст легенду для §4.
4. После 1+2: сверить полученные 100×42 байта с кандидатами из §4 и, если совпадут паттерны, легализовать byte-per-cell как формат хранения; затем — портировать в Defold (этап 7 [`PLAN.md`](../PLAN.md), пункты 21–22).

## 7. Прямой ответ на вопрос «найди описания уровней»
- **Формат описания уровня** установлен структурно: во время игры уровень занимает **42 байта подряд** в рабочем RAM (`0xAB35..0xAB5A` = сегмент 24 B + сегмент 18 B), загружается LDIR из верхней RAM (базы `0xC52A`/`0xC5CC`); сетка — 6×6. Раскладка *источников* (одна таблица на 42 B или две: 24 B + 18 B) ещё открыта (§1.1, §5).
- **Сами данные всех 100 уровней** в имеющихся образах не находятся напрямую: `.z80` усечён (таблицы вне захваченного диапазона), а в `BUMPY.TAP` непрерывной таблицы нужного размера нет (данные упакованы/генерируются). Получены **36 правдоподобных фрагментов** сеток как ориентир (§4).
- Для получения полных 100 описаний требуется один из шагов §5 (эмуляция+дамп RAM или дизассембли загрузчика и интерпретатора ячеек).

## 8. Словесное описание первого уровня (из `Bumpy-levels.png`)

Источник: [`Bumpy-levels.png`](../Bumpy-levels.png) — контактная таблица **10×10 = 100 экранов** (все 100 блоков уникальны по геометрии и хэшах). Блок `(столбец=0, строка=0)` = **уровень 1**. Расшифровка его пикселей выполнена [`tools/level_tool.js`](level_tool.js): `node tools/level_tool.js classify Bumpy-levels.png 0 0` / `floors ... 0 0` / `dump ... 0 0 <y> <y>`.

### 8.1. Структура экрана
- Экран в палитре ZX Spectrum (15 цветов на чёрном), рамка — белая (`#`).
- Слева и справа — тёмно-жёлтые (`y`) вертикальные полосы-«стены»/рамки поля (локальные x≈3..9 и 240..246).
- Верхний ряд — HUD: серые (`+`) текст-глифы + цифра голубым (`C`).
- Игровое поле: **6 горизонтальных линий платформ** (серые прямоугольники ~26×4 px, шаг по вертикали 32 px; локальные y = 29, 61, 93, 125, 157, 189). По горизонтали ячейки — слоты шириной **40 px** от x=14 (колонки 0..5: x=14, 54, 94, 134, 174, 214) → сетка **6×6**, как в спецификации [`tz.txt`](../tz.txt).

### 8.2. Платформы уровня 1 (подтверждено по пикселям каждой линии)
Каждый «этаж» (row = линия платформы, сверху вниз) имеет ровно один-два проёма:

| Этаж | Платформы (колонки) | Проём(ы) |
|---|---|---|
| 0 (верхний) | 0,1,2,3,4 | **5** |
| 1 | 1,3,4,5 | **0 и 2** |
| 2 | 0,1,2,3,4 | **5** |
| 3 | 1,2,3,4,5 | **0** |
| 4 | 0,1,2,3,4 | **5** |
| 5 (нижний) | 1,2,3,4,5 | **0** |

Визуально — «зигзаг»/лесенка: чётные этажи сдвинуты влево (проём справа), нечётные — вправо (проём слева). Падение в проём = смерть (по [`tz.txt`](../tz.txt) и этап 6 [`PLAN.md`](../PLAN.md)).

### 8.3. Спрайты над платформами (цвет и позиция, проверено по raw-пикселям)
Обозначение `этаж,колонка` — объект стоит в ячейке **над** указанной линией платформы (колонки 0..5 слева направо). Позиции сверены с точными x-диапазонами кластеров пикселей:

| Объект (цвет) | Позиция (этаж,кол) | px | Примечание |
|---|---|---|---|
| Серый глиф (`+`) | (0,0) | 46 | буква-глиф над верхней линией слева; вероятно элемент логотипа/надписи |
| Голубой (`C`) малый | (0,2), (4,4) | ~23 | компактный глиф |
| Тёмно-жёлтая полоса (`y`) | (0,4) | 52 | цвет = стена/рамка; вертикальный знак у правой части верхнего этажа |
| Жёлтый (`Y`) крупный | (1,1) | 83 | крупный объект над платформой (1,1) |
| Красный (`R`) | (1,2) | 50 | объект над платформой (1,2) |
| Голубой (`C`) | (1,5), (2,2), (4,3) | ~54 | один и тот же глиф в 3 местах; кандидат на «мяч»/повторяющийся предмет |
| Жёлтый (`Y») «B» | (2,0), (4,0) | ~49 | одинаковый глиф в двух местах; по форме — буква, декоративная надпись у левой стены |
| Красный (`R») «R» | (3,1) | 60 | буква-глиф, возможно декоративная |
| Жёлтый (`Y») малый | (2,4), (5,5) | ~44 | компактный глиф |
| Зелёный (`G») | (3,4) | 45 | объект над платформой (3,4) |

> Примечание: часть глифов в верхних этажах (серый знак, тёмно-жёлтая полоса) по форме и цвету похожи на элементы логотипа/рамки, а не на игровые предметы; их роль без эмулятора не установлена.

### 8.4. Честная оценка достоверности
- **Уверено (видно на пикселях):** сетка 6×6, расположение платформ/проёмов из §8.2 (проверено по координатам каждого прямоугольника), позиции и цвета спрайтов из §8.3.
- **Не установлено без эмулятора:** игровое поведение каждого цвета (мяч / предмет / тип платформы / стена). Крупные глифы «B»/«R» слева подозрительно похожи на буквы логотипа, а не на объекты уровня; голубой спрайт повторяется многократно — вероятно один тип объекта.
- **Как получить точное описание уровня 1 байтами:** эмуляция `BUMPY.TAP` (FUSE/zx70), дождаться старта уровня 1, дамп рабочего RAM `0xAB35..0xAB5A` (42 B) — см. §5, п.1.
