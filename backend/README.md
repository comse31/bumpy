# Backend Bumpy

Серверная часть для хранения профилей игроков и игрового прогресса.
Клиент игры (Defold, HTML5/wasm) продолжает сохранять всё локально
([`main/save.lua`](../main/save.lua), [`main/player_profile.lua`](../main/player_profile.lua)),
а модуль [`main/remote_db.lua`](../main/remote_db.lua) дублирует те же данные в БД.

## Выбор БД: SQLite

Используется **SQLite** — лёгкая встраиваемая СУБД:

- вся база — один файл `/data/bumpy.db`, отдельный сервер БД не нужен;
- нечего администрировать: нет пользователей, паролей, портов и бэкап-агентов;
- WAL-режим позволяет читать данные во время записи;
- ACID-транзакции на уровне файла;
- драйвер — стандартный модуль Python `sqlite3`, без ORM и сторонних зависимостей.

Для профилей игроков (десятки тысяч строк, простые запросы по первичному ключу)
этого достаточно; при росте нагрузки файл заменяется на PostgreSQL без изменения
схемы данных — SQL в [`app/repository.py`](app/repository.py) собран в одном месте.

## Имя и пароль игрока

Имя игрока **уникально** в БД (без учёта регистра), и по нему выполняется вход.

Сценарий первого посещения:

1. клиент просит имя по умолчанию (`GET /api/auth/next-name?player_id=...`);
   сервер выдаёт свободное `PlayerN` **и закрепляет его** за записью
   устройства — два новых устройства не получат одинаковое имя, а повторный
   запрос возвращает то же имя;
2. игрок может сразу задать пароль для этого авто-имени, **не меняя имя**:
   `POST /api/auth/login` с именем и паролем;
3. пароль сохраняется (PBKDF2), статусы остаются в записи устройства —
   прогресс не теряется;
4. при входе на другом устройстве под тем же именем пароль проверяется, а в
   ответе `login` приходит профиль: клиент подгружает из него текущие статусы
   (уровень, жизни, карман, рекорд).

Остальные правила:

- новое (свободное) имя — игра просит задать пароль и сохраняет его; если у
  устройства уже есть незакреплённая запись, она **переименовывается**, а не
  дублируется, поэтому прогресс сохраняется;
- имя уже есть — игра просит пароль и проверяет его; при неверном пароле имя
  откатывается к предыдущему;
- на устройстве, где игрок уже входил, пароль берётся из локального кэша
  (`bumpy_auth`) и **не запрашивается** (тихий вход при старте обновляет
  статусы из БД).

Пароль хранится только как PBKDF2-HMAC-SHA256: соль (16 байт), число итераций
и хэш в отдельных полях — открытого пароля в БД нет. Итерации задаются в
`config.yml` (`api.password_iterations`), у каждой записи своё значение,
поэтому их можно поднять без сброса старых паролей.

| Эндпоинт | Назначение |
|----------|------------|
| `POST /api/auth/check` | занято ли имя и задан ли для него пароль |
| `POST /api/auth/login` | вход или первичная привязка/смена пароля; в ответе профиль |
| `GET /api/auth/next-name` | свободное имя `PlayerN`; с `player_id` — закрепляет его за устройством |

`login` покрывает все сценарии: если имени нет, а своя запись устройства есть —
она переименовывается (прогресс сохраняется); если имени и записи нет —
создаётся новый игрок с паролем; если у автоматического имени пароля ещё нет —
он привязывается к существующей записи; если пароль задан — он проверяется.
В ответе всегда приходит профиль (`player`), чтобы клиент подгрузил статусы.

## Настройки БД (отдельный файл)

Все параметры вынесены в [`config.yml`](config.yml) — код не содержит ни путей,
ни лимитов. Относительные пути разрешаются от каталога конфига, поэтому
локальный запуск и контейнер работают с одним файлом. Путь к конфигу можно
переопределить переменной окружения `BUMPY_CONFIG`.

```yaml
database:
  path: /data/bumpy.db      # файл SQLite (в контейнере /data — docker-том)
  migrations_dir: migrations
  journal_mode: WAL
  synchronous: NORMAL
  busy_timeout_ms: 5000
  events: true              # писать историю событий игрока
```

Параметры паролей — в секции `api` того же файла:

```yaml
api:
  password_iterations: 120000  # PBKDF2, можно поднять без сброса паролей
  password_min_len: 4
  password_max_len: 32
```

## Схема данных

`players` — то же, что игра хранит локально, плюс идентификатор игрока:

| Поле | Источник в игре |
|------|-----------------|
| `player_id` | генерируется клиентом, хранится в `bumpy_player_id` |
| `name`, `visits` | `main/player_profile.lua` |
| `level`, `max_level`, `lives`, `drops`, `keys`, `hammers` | `main/save.lua` |
| `client_version`, `platform` | `game.project` / `sys.get_sys_info()` |
| `created_at`, `updated_at` | проставляет сервер |

`player_events` — история (`name`, `start`, `level`, `game_over`, `sync`).
Номер события (`id`) и время (`created_at`) проставляет сервер.

## API

Префикс `/api`. За nginx доступен по тому же адресу, что и игра (`/api/...`),
поэтому CORS не требуется.

| Метод | Путь | Описание |
|-------|------|----------|
| `GET` | `/api/health` | состояние сервиса и БД |
| `GET` | `/api/config` | публичные лимиты для клиента |
| `GET` | `/api/players?limit=&offset=` | лидерборд (по `max_level`, затем `visits`) |
| `GET` | `/api/players/{id}` | профиль + последние события |
| `PUT` | `/api/players/{id}` | создать/обновить профиль (идемпотентно) |
| `POST` | `/api/players/{id}/events` | добавить событие |
| `DELETE` | `/api/players/{id}` | удалить данные игрока |

Правила слияния при `PUT` (клиент может прислать снимок повторно):

- `null`-поля не затирают сохранённые значения;
- `max_level` только растёт — это рекорд, как в `main/save.lua`;
- `visits` не уменьшается.

Если в `config.yml` задан `api.api_key`, клиент обязан присылать заголовок
`X-Api-Key` (в игре — настройка `bumpy.api_key` в `game.project`).

## Локальный запуск

```bash
# из корня репозитория
docker build -f backend/Dockerfile -t bumpy-backend .
docker run --rm -p 8000:8000 -v bumpy-db:/data bumpy-backend
curl http://localhost:8000/api/health
```

Полный стек (игра + backend + БД):

```bash
docker compose -f docker/docker-compose.yml up -d --build
# игра: http://localhost:8080
# API:  http://localhost:8080/api/health
```

## Проверка

```bash
docker exec bumpy-backend python /tmp/smoke_test.py http://127.0.0.1:8000
```

Тест прогоняет реальные сценарии клиента: создание профиля, повторный `PUT`
(рекорд и визиты только растут), чтение с событиями, лидерборд, валидацию
и удаление.

## Развёртывание

[`deploy-master.yml`](../.github/workflows/deploy-master.yml) на `runs-on: [self-hosted]`:

1. создаёт сеть `bumpy-net` и том `bumpy-db` (если их ещё нет);
2. останавливает и удаляет старые контейнеры `bumpy-web` и `bumpy-backend`;
3. собирает оба образа;
4. запускает `bumpy-backend` с томом `bumpy-db:/data` и ждёт `/api/health`;
5. запускает `bumpy-web` и проверяет игру и `/api/health` через прокси nginx.

Миграции применяются при старте backend — отдельного шага деплоя для схемы нет.
Том `bumpy-db` при деплое **не удаляется**: данные игроков сохраняются.
